# 防风控约束

## 实测基线

2026-10-29 用本方案在同一登录态下连续访问：店铺列表页 3 次 + 天猫详情页 17 个 + 淘宝 C 店详情页 2 个，**零滑块、零验证码、零跳转拦截**。

## 为什么这套不容易触发风控

| 设计 | 原因 |
|---|---|
| 用用户本人已登录的真实 Chromium（ego lite） | 淘宝风控最认登录态与真实指纹，这一条强于任何 UA/指纹伪造 |
| 只读服务端渲染数据，零接口请求 | 请求量与真人逛店完全一致，没有额外 XHR 特征 |
| 串行单页复用，不并发不多开 | 并发是最典型的机器特征 |
| 单页随机 4–9 秒，每 6 个商品插 12–20 秒长停顿 | 打散等间隔节奏 |
| 逐条落盘、命中即停 | 中断可续，绝不重复请求已采页面 |

## 硬约束（不要突破）

1. **不调用 mtop 签名接口**：`h5api.m.tmall.com` 需要 `h5_tk` + `sign`，逆向属违反平台条款，且要跟着阿里改算法，收益为零（页面已带数据）。
2. **不上代理池批量轮换**：本场景不需要；代理反而让登录态与 IP 地域不一致，更容易被判异常。
3. **不开无头模式、不改指纹、不伪造 UA**：真实浏览器已是最优解；改动只会在 `navigator`/`webdriver` 类检测上留下痕迹。
4. **不并发**：`scripts/scrape.js` 是单页顺序导航，不要改造成多 Page 并行。
5. **不代填账号密码**：未登录时用 `task.handOff()` 让用户自己扫码，脚本不处理凭证。

## 节奏参数

| 参数 | 值 | 位置 |
|---|---|---|
| 单页基础等待 | 3500–6000 ms | `scrape.js` 首屏 |
| 滚动 + 二次等待 | 200–500 px / 500–1200 ms | `scrape.js` |
| 页间间隔 | 4000–9000 ms | `scrape.js` 循环尾部 |
| 长停顿 | 每 6 个商品 12000–20000 ms | 同上 |
| 单次任务上限 | ≤ 30 个链接 | 超过则分批，中间隔 10 分钟以上 |

## 停止条件

以下任一出现，立即停止本批次并如实告知用户，不要重试、不要换号、不要切代理：

- 页面标题或首屏文本命中 `验证 / 滑块 / 请稍等 / 访问受限 / 安全中心 / 亲，小二 / 登录后才能`
- 连续 2 个链接拿不到 `skuBase`（可能是限流降级，不一定是页面改版）
- 页面被重定向到登录页

`scrape.js` 命中关键词时写 `_run_summary.json` 的 `blocked: true` 并以退出码 3 结束。

## 环境坑

**`ERR_CONNECTION_CLOSED` 通常不是风控**。本次实测：系统代理（Clash 7897）把 `tmall.com` 走了代理导致连不上，而 `taobao.com` 正常；直连 tmall 返回 200。排查顺序应为：先 `curl --noproxy '*'` 直连目标域名，确认是代理规则问题，再考虑风控。
